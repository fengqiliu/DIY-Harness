# PACS 领域与迭代交付

工作台中的工作项跟踪产品变更，一个工作项选择一个主要限界上下文。在一个故事涉及多个系统时，根据业务规则的所有者选择主上下文，在交接记录中注明上游事实、下游责任和关联标识。以下模型供团队开展领域讨论，目标医院的系统边界及接口契约需要在对应项目确认。

| 限界上下文 | 主要对象与一致性规则 | 交接给其他上下文的事实示例 |
| --- | --- | --- |
| 检查登记 | 检查申请、登记记录。检查号按签发机构约定解释，变更关联需要保留依据。 | 检查已登记，向采集端提供可执行的检查信息。 |
| 影像归档 | 影像检查、序列与实例。分别使用 Study、Series、SOP Instance UID 标识，重复接收须遵循站点冲突策略。 | 某检查的影像已按约定可用，供阅片端查询。 |
| 阅片诊断 | 阅片任务、诊断草稿。切换患者或检查时清楚标识当前对象，保存时检查草稿版本。 | 已提交指定版本的诊断内容，供审核端处理。 |
| 报告审核 | 报告及版本。由有权用户执行退回、审核、签发或修订，各次决定可追溯。 | 指定报告版本已签发，供分发端消费。 |
| 结果分发 | 目标端投递记录。按报告版本和目的端识别投递，失败后可重试，保存回执。 | 目标端已确认接收，或投递待重试。 |
| 平台运维 | 部署版本、路由配置、队列和告警事件。发布与恢复均能定位到环境和版本。 | 某分发队列积压，或指定环境已恢复服务。 |

### 跨边界示例

用合成检查号 `DEMO-017` 演示“修订报告重新分发”。报告审核发布第二版后，结果分发为该版本与目标端建立投递记录。第一次超时后按站点策略重试。测试时分别核对审核履历、投递次数和目标端最终展示版本。检查号用于关联业务记录，DICOM Study Instance UID 用于定位影像，报告版本标识用于区分发布内容。

### 一个迭代如何使用

产品经理把故事写入待办并约定成功场景。项目经理结合容量与接口窗口选择迭代，将参与团队和依赖写进规划证据。设计、开发和测试可提前协作，每个阶段登记一名负责交付的人。需要对齐业务含义时，共同核对“报告已签发”“已投递”“目标端已确认”分别由谁记录、在何时成立。

日常同步从阻塞项入手，记录解除条件和证据。验收按故事核对真实观察范围。发布阶段记录演练或实际发布到达的环境。迭代评审用已交付条目演示完整场景，复盘把可验证的改进写入下一轮待办。六个交接阶段描述故事进度，一个迭代可以同时容纳多个处于不同阶段的故事。

## SDD 场景 · 修订报告重新分发

**示例规格 `PACS-DIST-001 v0.1`**　主限界上下文是结果分发，上游是报告审核，下游是 RIS。以合成检查号 `DEMO-017` 为例。当已签发的修订版 V2 取代 V1 后，RIS 用户最终可见 V2。遇到回执超时，运维人员能查到本次投递的状态和重试记录。验收时分别观察签发履历、投递记录和接收端展示版本。

### 领域契约

| 参与方 | 应提供的行为 |
| --- | --- |
| 报告审核 | 签发后提供报告标识、不可变版本标识，以及供版本排序的权威依据。历史版本保留可追溯。 |
| 结果分发 | 以「报告标识 + 版本标识 + 目的端」识别逻辑投递。重复事件沿用同一投递记录，重试沿用同一幂等键，同时保留各次尝试。 |
| RIS 或站点适配层 | 按站点契约处理幂等、版本顺序和回执，并可查询最终可见版本。HTTP 成功、业务接收和报告可见分别记录。 |

本场景拟采用「待投递 → 等待回执 → 业务已确认」作为正常状态路径。超时进入「待重试」，耗尽重试额度后转为「需人工处理」。回执形式、重试次数与间隔、目标端是否支持幂等和版本保护，由站点契约确定。能力缺失或待确认时，将对应验收项记录为阻塞，保留人工核对结果。

### 验收条件

| 编号 | 给定与操作 | 可观察结果 |
| --- | --- | --- |
| AC-01 | V1 已可见，审核方签发 V2 | 签发履历可查。结果分发为 V2 建立投递记录。RIS 最终可见 V2，并能核对匹配的业务接收证据。 |
| AC-02 | V2 已投递且业务回执超时，按约定重试 | 沿用版本、目的端和幂等键，新增尝试记录。若目标端已处理上次请求，重试后仍只呈现一份当前 V2。 |
| AC-03 | V2 签发事件重复到达 | 同一目的端保留一条逻辑投递。已有业务确认时不再发起投递。 |
| AC-04 | V2 已可见，V1 的迟到回执或请求随后到达 | 迟到回执归入 V1 履历。V1 不覆盖 V2，V2 的确认状态不受影响。 |
| AC-05 | 目标端持续不可用，达到站点约定的重试上限 | 工作台可查看人工处理状态、版本、目的端和失败原因。恢复后按授权处理并保留证据。 |

AC-05 中的状态查看属于拟建的 PACS 分发业务界面。本 Harness 承载研发工作项、规格引用和证据记录。

### 六角色交接

| 阶段 | 检查点登记内容 |
| --- | --- |
| 产品经理 · 需求发现 | 记录规格编号、版本、业务目标和 AC-01 至 AC-05。 |
| 项目经理 · 迭代计划 | 把签发事件、分发状态与 RIS 契约拆成可验证切片，写明迭代、接口依赖和验收环境。 |
| UI/UX 设计师 · 交互设计 | 给出等待回执、待重试和人工处理的页面状态，明确谁能重试以及按钮反馈。关联 AC-02 与 AC-05。 |
| 开发工程师 · 开发实现 | 关联 AC-01 至 AC-05 对应的代码差异和检查结果，说明幂等、迟到消息和失败恢复的处理位置。 |
| 测试工程师 · 验收验证 | 逐项记录测试环境、输入、预期、实际结果和证据。对 RIS 可见性单独取证。 |
| 运维工程师 · 发布运维 | 记录交付版本、站点契约、积压和失败监控、重放或恢复演练。 |

在工作台新建「修订报告重新分发」，选择「结果分发」。每次交接引用规格版本和验收编号，例如 `PACS-DIST-001 v0.1 / AC-02`，再附设计稿、代码差异或实测证据。验收失败按现有流程退回开发。业务口径改变时先确认新版本和受影响的 AC，再按新版本补齐交接和复验记录。
